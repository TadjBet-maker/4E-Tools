# 4E Tools --- DECISIONS

-   D-001: Название --- 4E Tools; без `by VLAD 4E`.

-   D-002: Первая платформа Android; кодовая база не блокирует iOS.

-   D-003: React Native + Expo + TypeScript strict; Supabase/PostgreSQL.

-   D-004: После login сразу главный каталог; обязательного выбора
    склада нет. Главный UX LOCKED.

-   D-005: Категория → модель → физический экземпляр → действие.

-   D-006: Видимые номера 1.1/1.2; UUID отдельный. QR не нужен для MVP.

-   D-007: movements --- исторический append-only журнал по смыслу.

-   D-008: Dark/Light имеют один UX.

-   D-009: Mobile-first, включая администратора.

-   D-010: TAKE/RETURN атомарны и серверно подтверждаются.

-   D-011: Возврат возможен на другой склад.

-   D-012: DAMAGED/REPAIR не доступны к выдаче.

-   D-013: Исторические сущности не удаляются так, чтобы ломать связи.

-   D-014: Git + код + AI/\* --- источник контекста между моделями.

-   D-015: Навигация --- Expo Router.

-   D-016: Server state --- TanStack Query + Supabase client. Не вводить
    Redux без новой необходимости.

-   D-017: Темизация --- design tokens + React Context; выбор темы
    хранится в AsyncStorage.

-   D-018: Тесты --- Jest + React Native Testing Library; SQL/RPC
    integration tests для TAKE/RETURN/RLS.

-   D-019: `app/` используется для маршрутов Expo Router; основная
    реализация находится в `src/` (`components`, `features`, `lib`,
    `theme`, `types`). Supabase migrations --- в `supabase/`.

-   D-020: Клиентские env: `EXPO_PUBLIC_SUPABASE_URL`,
    `EXPO_PUBLIC_SUPABASE_ANON_KEY`. `.env` не коммитится;
    `.env.example` коммитится. Service role только в доверенной
    серверной среде.

-   D-021: Бригады входят в MVP. Есть `brigades` и
    `profiles.brigade_id`; brigadier видит свою бригаду.

-   D-022: WRITTEN_OFF входит в модель MVP и админский workflow. LOST
    --- post-MVP.

-   D-023: Вход в UI выполняется по логину, не по email. Supabase Auth
    использует технический email вида `<login>@4e.local`; пользователь
    его не видит. `profiles.login` --- UNIQUE NOT NULL. Преобразование
    login→technical email выполняется единообразно в auth-слое.

-   D-024: «Забыли пароль?» в MVP показывает «Обратитесь к
    администратору». Самостоятельный reset password --- post-MVP.

-   D-025: Splash и Login всегда используют фирменную тёмную тему. После
    успешного входа приложение использует выбранную пользователем
    Dark/Light тему.

-   D-026: Язык MVP --- русский. Пользовательские строки не размазывать
    по компонентам; хранить централизованно в `src/strings/`.

-   D-027: Брендинг LOCKED: логотип, app icon, splash и утверждённая
    палитра Dark/Light. Утверждённые слоганы: «Весь инструмент под
    контролем» и «Строй с уверенностью». Ассеты --- `assets/branding/`.
    Визуальные исходники должны быть добавлены в репозиторий до
    pixel-perfect реализации.

-   D-028: `profiles.position` --- nullable свободный текст. Отдельный
    справочник должностей в MVP не вводится.

-   D-029: «Просроченные» и сроки возврата --- post-MVP. `due_at` в MVP
    отсутствует; UI не должен показывать рабочий таб «Просроченные».

-   D-030: «Сервис» в MVP не является отдельным warehouse. Для `REPAIR`
    UI показывает «На ремонте» без складской локации. Отдельные
    сервисные центры/локации --- post-MVP.

-   D-031: Административная карточка физического экземпляра в MVP
    поддерживает необязательные `serial_number`, `purchase_date`,
    `note`.

-   D-032: Нумерация экземпляров хранится структурно:
    `tools.slot integer NOT NULL`, `UNIQUE(model_id, slot)`.
    `inventory_number` не присылается клиентом; отображаемый номер
    формируется из `tool_models.inventory_group || '.' || tools.slot`.
    Создание экземпляра выполняет RPC `create_tool`, который сериализует
    создание для выбранной модели, вычисляет следующий slot и создаёт
    запись атомарно. Это исключает коллизии при одновременной работе
    администраторов.

-   D-033: В Supabase Auth подтверждение email для этого закрытого
    корпоративного приложения отключено. Саморегистрации в мобильном
    клиенте нет. Аккаунты создаются администратором через доверенную
    серверную среду с service-role; service-role никогда не попадает в
    приложение. `login` регистронезависим и хранится как PostgreSQL
    `citext` с UNIQUE.

-   D-034: Бригадир видит текущие назначения и разрешённую историю
    пользователей, которые сейчас состоят в его бригаде. Историческое
    членство в бригаде в MVP не снапшотится. При переводе сотрудника его
    доступная бригадиру история следует текущему членству.

-   D-035: Административные переходы состояния в MVP выполняются только
    через атомарные RPC: `send_to_repair`, `return_from_repair`,
    `write_off`. Все принимают `request_id` и используют ту же
    идемпотентность, блокировку строки и запись movement, что
    TAKE/RETURN. Прямой клиентский UPDATE критического состояния tools
    запрещён.

-   D-036: Создание `tool_models` выполняется только через атомарный RPC
    `create_tool_model`. RPC блокирует выделенную строку/ресурс
    нумерации, вычисляет следующий
    `inventory_group = MAX(inventory_group)+1`, создаёт модель и
    возвращает её. Клиент не присылает `inventory_group`; прямой INSERT
    в `tool_models` из мобильного клиента запрещён. UNIQUE остаётся
    дополнительной защитой.

-   D-037: Persistent server-state cache (MMKV / AsyncStorage persister
    для TanStack Query) не входит в MVP. В MVP TanStack Query держит
    server-state cache только в памяти процесса. Локально сохраняется
    только выбранная тема и другие явно разрешённые пользовательские
    настройки.

-   D-038: Все mutating RPC, включая `create_tool_model` и
    `create_tool`, фиксируют событие в `movements`. Enum
    `movements.action` расширяется значениями `CREATE_MODEL` и
    `CREATE_TOOL`. Идемпотентность всех mutating RPC обеспечивается
    единообразно через `UNIQUE(actor_user_id, request_id)`: при повторе
    того же `request_id` RPC возвращает результат ранее выполненной
    операции и не создаёт дубль.

-   D-039: В MVP полный жизненный цикл конкретного экземпляра
    инструмента (`tool history`) доступен только admin. Employee видит
    только собственные movements. Brigadier видит movements
    пользователей своей текущей бригады согласно D-034. Отдельного
    публичного экрана полной истории инструмента для employee/brigadier
    в MVP нет.
